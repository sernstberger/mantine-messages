## Installation

<InstallScript packages="mantine-messages" />

Import the styles once, next to Mantine's:

```tsx
import '@mantine/core/styles.css';
import 'mantine-messages/styles.css';
```

`mantine-messages` has one entry and no dependency on a markdown library. To show markdown (in
`MarkdownBody`, and in the answers of `AssistantThread`), install a markdown engine yourself and
give it to the package through an adapter, as `@mantine/code-highlight` does for highlighters; see
Markdown adapter below. The examples use react-markdown and remark-gfm:

<InstallScript packages="react-markdown remark-gfm" />

The one `styles.css` covers the whole package.

## Usage

`Inbox`, `ChatThread` and `Composer` share one set of types: `Conversation`, `Message` and
`MessagesUser`. You bring the data; the components never fetch anything.

## ChatThread

`ChatThread` takes messages oldest first. Consecutive messages from one person within
`groupWindow` (5 minutes by default) share one group, each new day gets a divider, and the
messages of `currentUserId` sit on the right. The status of your last message shows under it;
"Sending" and "Not sent" show under every message that has them.

Screen readers hear who wrote each message ("You" for your own, `labels.you`) and when, also
where the screen shows no name or time; times are `<time datetime>` elements.

`ChatThread` scrolls itself (it is a Mantine `ScrollArea`), so give it a height or let it fill a
flex column with `style={{ flex: 1 }}`. It opens at the newest message and follows new ones while
the user is at the bottom, or when they sent the message. While they read older messages it stays
put, and loading older messages at the top never moves the view. Set `autoScroll={false}` to turn
this off.

### Custom messages

`renderMessage` draws a whole message from the parts of `ChatThread`: `ChatThread.Message` (the
row, with the avatar and the author's name), `ChatThread.Quote`, `ChatThread.Bubble`,
`ChatThread.Actions`, `ChatThread.Attachments`, `ChatThread.Reactions` and `ChatThread.Meta`. It
gets the message and where it sits (`own`, `groupStart`, `groupEnd`, `highlighted`, `lastOwn`,
`original` and `jumpTo`). Each part takes its data from the row, keeps the screen reader text of
the default, and is styled by the thread's Styles API, so `classNames` and the theme reach custom
rows too. Without children, `ChatThread.Message` renders the default row; `avatar` and the
bubble's `actions` take a part or `null`. For the body alone, `renderBody` is shorter.

```tsx
<ChatThread
  messages={messages}
  users={users}
  currentUserId="me"
  renderMessage={(message, context) => (
    <ChatThread.Message message={message} context={context} avatar={null}>
      <ChatThread.Quote />
      <ChatThread.Bubble actions={<ChatThread.Actions actions={['copy']} />}>
        <MarkdownBody>{message.body}</MarkdownBody>
      </ChatThread.Bubble>
      <ChatThread.Meta />
    </ChatThread.Message>
  )}
/>
```

## Replies

A message with `replyToId` shows the message it answers above its bubble: a caption such as
"You replied to Maya" and a faded copy of the original. A click on the copy scrolls to the
original and flashes it. Pass `onReply` to `ChatThread` to show a reply button beside each message,
then give the chosen message to `Composer` as `replyTo`; it shows a "Replying to" bar, focuses the
box, and calls `onCancelReply` on its close button or Escape.

```tsx
const [replyTo, setReplyTo] = useState<Message | null>(null);

<ChatThread messages={messages} users={users} currentUserId="me" onReply={setReplyTo} />
<Composer
  replyTo={replyTo && { id: replyTo.id, authorName: nameOf(replyTo.authorId), body: getPreview(replyTo) }}
  onCancelReply={() => setReplyTo(null)}
  onSend={(draft) => {
    send({ body: draft.text, replyToId: draft.replyToId });
    setReplyTo(null);
  }}
/>
```

## Actions, reactions and files

`actions` sets the buttons beside each message: built-ins (`'reply'`, `'react'`, `'thread'`,
`'edit'`, `'copy'`) show when their handler is set, and custom items `{ id, label, icon, onClick }`
always show. After three, the rest go in a menu. Reactions and attachments on a message render
under its bubble; pass `onToggleReaction` and `onOpenAttachment` to make them interactive.
Image attachments load lazily; give them `width` and `height` (in pixels) when you know them, so
their space is kept before they load and the thread does not jump.

The buttons of a message form a toolbar with one tab stop: Tab reaches the first button (or the
one used last), the arrow keys move between them, Home and End jump to the ends, and Tab moves on
to the next message. The toolbar and its menu button are named after the message's author, "More
actions for Maya's message" or "for your message" (`labels.more` and `labels.toolbar` are
functions of `{ author, own }`). The menu mounts on first use. The copy action copies the whole
`body`, markdown included; button labels use the plain-text preview.

## Long threads

Pass `onLoadOlder`, `hasOlder` and `loadingOlder` to load history as the user scrolls up; the view
stays where it was while older messages are added above. `unreadAfterId` draws a "New messages"
line after the last read message; its text is `labels.newMessages`, the same key on `MessageList`,
`ChatThread`, `TeamThread` and `ThreadPanel.Replies`, so one translation object fits them all.

The list is a `role="log"` named by `labels.log` ("Messages"), or by `aria-label` when you pass
one. While older messages load, and in the update that adds them, it is `aria-busy`, so screen
readers do not read the whole page of history out as new messages; the loader at the top is
labelled `labels.loadingOlder`.

### Windowing

Every message of a thread is in the page by default, which is right for most threads. It stops
being right at a few thousand messages. Measured with `ChatThread` in a 600px panel (production
build, Chromium, Firefox and WebKit):

- 1,000 messages: opens in 0.2 to 0.4 s, 11,000 DOM nodes, a new message shows in under 30 ms
- 2,500 messages: opens in 0.4 to 0.8 s, 28,000 nodes, a new message in 26 to 63 ms; still
  comfortable
- 5,000 messages: opens in 0.8 to 1.5 s, 55,000 nodes, a new message in 64 to 128 ms
- 10,000 messages: opens in 1.7 to 3.9 s, 114,000 nodes, 239 MB of JavaScript heap (Chromium), a
  new message in 191 to 342 ms, and scrolling drops to 20 frames a second in WebKit

Below about 2,500 messages, leave it as it is, and page history in with `onLoadOlder`. Above that,
render only the rows in view. Like Mantine's own `Combobox`, `Tree` and `Table`, mantine-messages
does not ship a virtualizer: you bring one, and `MessageList` gives it what it needs. Pass a
`rowsComponent` to `MessageList`, `ChatThread`, `TeamThread` or `AssistantThread`. It receives:

- `rows`: every row, oldest first, as data: items, date dividers and the unread line, each with a
  `key` (an item's `id`)
- `viewportRef`: the scrolling element, for the virtualizer's `getScrollElement`
- `handlersRef`: set `{ scrollToIndex }` on it, so `jumpTo` can reach a message that is not
  rendered

Render each row in view with `MessageList.Row`, which takes `style` and `ref` to position and
measure it. The list keeps its chat behaviour with a window: it opens at the newest message and
follows new ones, keeps the message you are reading in place when older ones load above, and
`jumpTo` scrolls to a message outside the window, waits for it to render, then focuses and flashes
it. The demo uses [@tanstack/react-virtual](https://tanstack.com/virtual/latest), the virtualizer
Mantine's docs recommend, on 10,000 messages; it opens in 58 ms in Chromium, with 321 DOM nodes and
17 MB of heap, and a new message shows in 9 ms. `initialOffset` starts the virtualizer at the end,
where the list opens.

<Demo data={demos.longThread} />

With a window, only the rendered rows are in the accessibility tree. The list is still a
`role="log"` with polite announcements, so new messages are read out, but a screen reader's browse
cursor reaches only the messages near the view, and focus on a message is lost when it scrolls far
out of the window. `jumpTo` with `focus` (the default) brings a message into the window and
focuses it, so search results and reply quotes still lead keyboard and screen reader users to the
message.

## Building your own layout

`MessageList` is the engine under `ChatThread`: give it any items with `id`, `authorId` and
`createdAt` and a `renderItem`. It adds date dividers, groups (with `groupWith`), the unread line,
scrolling and jumps.

```tsx
const renderNote = useCallback(
  (note: Note, { groupStart }: MessageListItemContext<Note>) => (
    <NoteRow note={note} showName={groupStart} />
  ),
  []
);

<MessageList
  items={notes}
  groupWith={(previous, note) => previous.authorId === note.authorId}
  renderItem={renderNote}
/>
```

Each item is memoised on the item, its neighbours and its context, so when the list renders again
only new and changed items render. That needs a stable `renderItem`: wrap it in `useCallback` or
define it outside the component. A new function on every render still works, but renders every
item each time.

`ChatThread` and `TeamThread` do this for you: their rows render again only when their message,
group or status changes. Handlers such as `onReply` may be new arrows on every render; they are
always called in their newest form. Keep `renderBody`, `renderMessage`, `actions`, `labels`, `users` and the Styles
API objects stable (or defined outside the component), since a change to one of them renders
every row.

Inside `renderItem`, `jumpTo(id)` scrolls to an item, flashes it (`highlighted` is true for 1.6
seconds) and moves keyboard focus to it, so screen readers read it and Tab continues from there.
Pass `jumpTo(id, { focus: false })` when focus must stay put, for example while the user types in
a search box that jumps to matches. To jump from outside the list, for example from a sidebar, pass `handlersRef`; it gets
`{ jumpTo }`. `ChatThread`, `TeamThread` and `AssistantThread` take `handlersRef` too and pass it to
their list.

```tsx
import { useRef } from 'react';
import { MessageList, type MessageListHandlers } from 'mantine-messages';

const list = useRef<MessageListHandlers>(null);

<MessageList handlersRef={list} items={notes} renderItem={renderNote} />
<Button onClick={() => list.current?.jumpTo('n42')}>Show the first reply</Button>
```

## Panes

`MessagesShell` puts the panes of a messaging app side by side: `MessagesShell.List` (300px,
change it with `w`), `MessagesShell.Main` (the rest of the width) and `MessagesShell.Aside`
(280px), each optional. It fills the height you give it, draws the borders between panes, and
each pane is a labelled region (`aria-label` names it). `withBorder` and `radius` frame the whole.

The shell measures itself. Below `asideBreakpoint` (960px by default, `0` never) the aside hides
and `MessagesShell.AsideToggle`, which renders nothing while there is room, opens it over `Main`;
Escape or a click beside it closes it. Control it with `asideOpened` and `onAsideOpenedChange`,
for example to open a thread panel as soon as a thread is picked. The Messenger demo above and the
work queue below are built on it.

```tsx
<MessagesShell withBorder radius="lg" h={600}>
  <MessagesShell.List aria-label="Conversations">
    <ScrollArea style={{ flex: 1 }}>
      <Inbox conversations={conversations} value={selected} onChange={setSelected} />
    </ScrollArea>
  </MessagesShell.List>
  <MessagesShell.Main aria-label="Conversation">
    <Group justify="space-between" px="md" py="sm">
      <Text fw={600}>{title}</Text>
      <MessagesShell.AsideToggle />
    </Group>
    <ChatThread messages={messages} users={users} currentUserId="me" style={{ flex: 1 }} />
    <Composer onSend={send} m="sm" />
  </MessagesShell.Main>
  <MessagesShell.Aside>{details}</MessagesShell.Aside>
</MessagesShell>
```

## Team chat

`TeamThread` shows Slack-style rows: avatar, name and time on the first message of a group, and
compact follow-ups whose time shows on hover. It takes `ChatMessage` and `SystemEvent` items;
events such as "Priya joined #launch" are centred lines that break groups. A message with `thread`
shows "12 replies" with the people who answered and calls `onOpenThread`; `editedAt` adds
"(edited)", and `visibility: 'internal'` marks an internal note. On hover each message shows React,
Reply in thread, and a menu with Edit (your own messages) and Copy.

Pass channel messages only; thread replies (messages with `threadId`) go to `ThreadPanel`. The
panel is a frame: a header with `title` ("Thread" by default) and `subtitle`, then its children.
`ThreadPanel.Replies` shows the parent, a reply count and the replies; it takes every `TeamThread`
prop but `items` and `threadParentId` (`parent` and `replies` instead), so actions, `labels`,
`hasOlder`, `loadingOlder`, `onLoadOlder`, `handlersRef`, `groupWindow` and `autoScroll` go on it.
`ThreadPanel.Footer` pads your `Composer` under the replies; any other child renders as it is.

The title is an `h2` heading that names the panel; set `titleOrder` to fit your page's outline.
The close button shows when `onClose` is set (or with `withCloseButton`), takes
`closeButtonProps`, and its label is `labels.close`.

Keyboard and screen readers: when the panel opens (or `ThreadPanel.Replies` shows another
thread) from a focused control, such as a thread summary, focus moves to its title, and when it
closes with focus inside it, focus goes back to that control. Nothing moves when the panel is
already open as the page loads. Turn this off with `withFocusManagement={false}` if your app moves
focus itself. Escape does not close the panel: it is a side region next to the channel, not a
dialog, and Escape inside its composer belongs to the composer. Add it with `onKeyDown` if your
layout wants it.

```tsx
const channelItems = items.filter((item) => 'kind' in item || !item.threadId);
const replies = messages.filter((message) => message.threadId === open?.id);

<TeamThread
  items={channelItems}
  users={users}
  currentUserId="me"
  selectedId={open?.id}
  onOpenThread={setOpen}
/>
{open && (
  <ThreadPanel subtitle="#launch" onClose={() => setOpen(null)}>
    <ThreadPanel.Replies parent={open} replies={replies} users={users} currentUserId="me" />
    <ThreadPanel.Footer>
      <Composer onSend={(draft) => reply(open.id, draft)} />
    </ThreadPanel.Footer>
  </ThreadPanel>
)}
```

### Custom team messages

`TeamThread` takes `renderBody` for the text of a message, and `renderMessage` for whole items.
`renderMessage` gets messages and events alike: render events (items with `kind`) with
`TeamThread.Event` and messages with `TeamThread.Message`, the row with the avatar or the hover
time. Its parts are `TeamThread.Author`, `TeamThread.Text`, `TeamThread.Attachments`,
`TeamThread.Reactions`, `TeamThread.ThreadSummary` and `TeamThread.Actions` (the `actions` slot of
the row, `null` for none); they share the thread's Styles API and labels.

```tsx
<TeamThread
  items={items}
  users={users}
  currentUserId="me"
  renderMessage={(item, context) =>
    'kind' in item ? (
      <TeamThread.Event event={item} />
    ) : (
      <TeamThread.Message message={item} context={context}>
        <TeamThread.Author />
        <TeamThread.Text>
          <MarkdownBody>{item.body}</MarkdownBody>
        </TeamThread.Text>
        <TeamThread.ThreadSummary />
      </TeamThread.Message>
    )
  }
/>
```

## Message parts

`Message` is the row `TeamThread` draws, for your own layouts: an avatar column and a content
column. Its parts share one Styles API.

```tsx
<Message compact={!groupStart}>
  {groupStart ? <Message.Avatar name={author.name} src={author.avatar} /> : <Message.Meta>9:41</Message.Meta>}
  <Message.Body>
    {groupStart && <Message.Meta>{author.name} · 9:41</Message.Meta>}
    {note.text}
  </Message.Body>
</Message>
```

## Markdown adapter

`MarkdownBody` renders markdown with Mantine `Typography` styles. The package does not bundle a
markdown engine: an adapter turns the text into elements. Without one, `MarkdownBody` shows the
text as it is, with its line breaks, so nothing is lost and nothing needs installing. Install
`react-markdown` and `remark-gfm` (see above), create the adapter once at module level and wrap
your app in `MarkdownAdapterProvider`:

```tsx
import Markdown from 'react-markdown';
import remarkGfm from 'remark-gfm';
import { createReactMarkdownAdapter, MarkdownAdapterProvider } from 'mantine-messages';

const adapter = createReactMarkdownAdapter(Markdown, { remarkPlugins: [remarkGfm] });

function Root({ children }: { children: React.ReactNode }) {
  return <MarkdownAdapterProvider adapter={adapter}>{children}</MarkdownAdapterProvider>;
}
```

With react-markdown the result renders GitHub flavoured markdown (tables, task lists,
strikethrough). It is safe by default: raw HTML shows as text and never becomes elements,
`javascript:` links are dropped, links open in a new tab with `rel="noreferrer"`, and code blocks
show their language and a copy button. `MarkdownBody` keeps all of that, its labels and its Styles
API whatever the engine is. Pass `adapter` to one `MarkdownBody` to use another engine there.

`ChatThread` shows `body` as plain text. Render markdown messages with `renderBody`:

```tsx
import { ChatThread, MarkdownBody } from 'mantine-messages';

<ChatThread
  messages={messages}
  users={users}
  currentUserId="me"
  renderBody={(message) =>
    message.format === 'markdown' ? <MarkdownBody>{message.body}</MarkdownBody> : message.body
  }
/>
```

Replace a built-in renderer with `components` of `createReactMarkdownAdapter`, for example code
blocks highlighted by `@mantine/code-highlight`:
`createReactMarkdownAdapter(Markdown, { remarkPlugins: [remarkGfm], components: { pre: HighlightedPre } })`.
Other remark plugins go in `remarkPlugins`, after `remarkGfm`.

To use another engine, write an adapter: an object with `render(markdown, renderers)`, which
returns the elements of one block of text and may use the Mantine `renderers` (`a`, `code` and
`pre`) that `MarkdownBody` passes in, and an optional `splitBlocks`. `plainTextMarkdownAdapter` is
the default, and the shortest example.

`MarkdownBody` renders its text block by block (blocks end at blank lines outside code fences, and
lists stay whole) and keeps each rendered block while its text and adapter are the same. A streamed
answer re-parses only its last block per token instead of the whole answer, and a re-render with
the same text renders nothing again. Keep the adapter stable (module level or `useMemo`): a new
object renders everything again. When a remark plugin can change where blocks end, pass
`splitBlocks: false` to `createReactMarkdownAdapter`, and the text is rendered whole; text with link
reference or footnote definitions is rendered whole too.

## Assistant

`AssistantThread` is a chat with a model: prompts are compact bubbles on the right, answers are
full width. It renders text with `MarkdownBody`, so answers show as plain text until you wrap the
app in a `MarkdownAdapterProvider` (see Markdown adapter above); the demo below does.

Each `AssistantMessage` has a `role` (`'user'` or `'assistant'`) and `parts`, rendered in order:
`text` (markdown), `reasoning` and `tool`. Reasoning and tools are collapsible steps; a tool shows
its state (running, done, failed) and, when opened, its input and output as JSON.

To stream, set the answer's `status` to `'streaming'` and update its last part as tokens arrive.
Answers and prompts are memoized on the message object, so a token renders only the streaming
answer (which re-parses only its last markdown block), and a cursor blinks at its end. Replace a
message with a new object when it changes, as below, rather than changing it in place. Inline
`onRegenerate`, `onEdit` and `labels` are fine: they do not render finished answers again. The list follows the answer as it grows while the user is at the bottom. Finish with
`'done'`, or `'error'` with an `error` text to show an alert with Retry.

```tsx
setMessages((current) => {
  const answer = current[current.length - 1];
  const parts = [...answer.parts];
  const last = parts[parts.length - 1];
  parts[parts.length - 1] = { ...last, text: `${last.text}${token}` };
  return [...current.slice(0, -1), { ...answer, parts }];
});
```

- Stop: pass `streaming` and `onStop` to `Composer`; its send button becomes a stop button
- Regenerate: `onRegenerate(message)` shows Regenerate on the last answer and Retry on an error
- Edit and resend: `onEdit(message, text)` lets the user edit a prompt in place; drop the answers
  after it and ask again

Screen readers: the list is a `role="log"` with `aria-live="off"`, so tokens are not read out.
When an answer starts, a visually hidden status region says `labels.thinking` once, and the answer
is `aria-busy` while it streams; when it finishes, its text goes to the status region and is read
once. Errors are read by their alert. After editing a prompt, Escape or Cancel returns focus to its
Edit button, and sending focuses the prompt (or the newest prompt, when the app replaced it).

## Inbox

`Inbox` lists conversations with a preview of the last message, its time and an unread count.
Use `value` and `onChange` to control which one is open, or `defaultValue` to leave it to the
component.

`withSearch` adds a search box that filters by title (`searchValue`, `defaultSearchValue` and
`onSearchChange` control it). `sections` groups the list: `true` gives Pinned, Channels and Direct
messages from `pinned` and `kind`, or pass `{ id, label, match }` objects; each conversation goes in
the first section that matches. Channels show a `#`.

Screen readers hear an unread count as words (`labels.unread(count)`, "3 unread") instead of the
badge's bare number, and "Muted" (`labels.muted`) after a muted conversation. While the search
filters the list, a visually hidden status region says how many conversations match
(`labels.results(count)`, or `labels.noResults`) once typing pauses for 300ms. Rows are memoized,
so typing in the search box renders no row again; keep `conversations` and `sections` the same
objects between renders.

## Composer

`Composer` grows with its text up to `maxRows`. Enter sends, Shift+Enter adds a line. `onSend`
gets a draft: `{ text, format, mode, replyToId }`, with the text trimmed.
After sending, by Enter or with the button, the cursor stays in the box. With `replyTo`, the reply
bar describes the box (`aria-describedby`), so screen readers say whom the message answers when
the box gets focus.

`modes` adds a switch above the box, for example Reply and Internal note; the chosen `value` goes in
`draft.mode`. A mode with `note: true` tints the composer yellow, and its `placeholder` replaces the
usual one.

```tsx
<Composer
  modes={[
    { value: 'reply', label: 'Reply' },
    { value: 'note', label: 'Internal note', color: 'yellow', note: true, placeholder: 'Only teammates see notes' },
  ]}
  onSend={(draft) => send({ body: draft.text, visibility: draft.mode === 'note' ? 'internal' : 'public' })}
/>
```

The text box is reachable like a Mantine input's: `inputRef` gets the `textarea` (to focus it after
a click elsewhere), `textareaProps` goes to the `Textarea` (`name`, `maxLength`, `autoFocus`,
`onPaste` and so on; its `onChange` and `onKeyDown` run after the composer's own), and `readOnly`
keeps the text selectable but stops editing and sending.

```tsx
const inputRef = useRef<HTMLTextAreaElement>(null);

<Composer inputRef={inputRef} textareaProps={{ maxLength: 2000, onPaste: attachPastedFiles }} />
```

## Theming

Every component reads its size, radius and colors from the Mantine theme, and the props below
override them for one instance. `radius` takes a key of `theme.radius` or any CSS length;
`color` takes a key of `theme.colors` or any CSS color; sizes take `xs` to `xl`, and where a
pixel size makes sense (`avatarSize`) a CSS length or a number too.

- `ChatThread`: `radius` (bubbles and quotes), `color` and `autoContrast` (your bubbles) and
  `avatarSize`
- `TeamThread` and `Message`: `avatarSize`; `Message` also takes `radius` for its avatar
- `Inbox`: `radius`, `color`, `variant` and `autoContrast` (the open conversation, resolved like
  Mantine's `NavLink`)
- `Composer`: `size` and `radius`
- `Reactions`: `radius` and `color`; `Attachments`, `AssistantThread` and `MessagesShell`: `radius`
- `MessageActions`: `size`, `radius`, `variant` and `color`, passed to its buttons

The demo below themes a thread and its composer with two controls.

<Demo data={demos.theming} />

The props set CSS variables on the root element, named `--<component>-<name>`: for example
`--chat-thread-radius`, `--chat-thread-own-bg`, `--inbox-active-bg` and
`--messages-shell-aside-width`. The Styles API tab of each component lists its variables. Set them
with the `vars` prop (a function of the theme and the component's props), in a CSS file, or for
every instance with `Component.extend({ vars })` in `createTheme`.

```tsx
import { createTheme, MantineProvider } from '@mantine/core';
import { ChatThread, Inbox } from 'mantine-messages';

const theme = createTheme({
  components: {
    ChatThread: ChatThread.extend({
      defaultProps: { radius: 'md', color: 'teal' },
    }),
    Inbox: Inbox.extend({
      vars: (theme, props) => ({ root: { '--inbox-radius': theme.radius.xs } }),
    }),
  },
});
```

## Compound components

The components that have many parts follow the compound pattern of `@mantine/lightbox` and
`@mantine/core`: the parts are static members of the component, share its Styles API (`classNames`,
`styles`, `unstyled` and `attributes` of the root reach them) and read their data from the nearest
row or panel, so they work only inside it. Without children, the row and the panel render their
default content.

- `ChatThread.Message`, `.Avatar`, `.Quote`, `.Bubble`, `.Actions`, `.Attachments`, `.Reactions`
  and `.Meta`, inside `renderMessage`
- `TeamThread.Message`, `.Author`, `.Text`, `.Attachments`, `.Reactions`, `.ThreadSummary`,
  `.Actions` and `.Event`, inside `renderMessage`
- `ThreadPanel.Replies` and `ThreadPanel.Footer`, inside the `ThreadPanel` frame
- `MessagesShell.List`, `.Main`, `.Aside` and `.AsideToggle`
- `Message.Avatar`, `.Body` and `.Meta`

Each part has its own props type, and every component has a type namespace, as in Mantine:
`ChatThread.Props`, `ChatThread.StylesNames`, `ChatThread.Factory`, `ChatThread.CssVariables` and
`ChatThread.Labels`, and for parts `ChatThread.Bubble.Props` and `ChatThread.Bubble.StylesNames`.
The context given to `renderMessage` is typed `ChatThreadMessageContext` and
`TeamThreadMessageContext`.

```tsx
import type { ChatThread, TeamThread } from 'mantine-messages';

type BubbleProps = ChatThread.Bubble.Props;
type ThreadSelectors = TeamThread.StylesNames;
```

## Labels

Every text the package adds is a label, so an app in another language changes no component. Each
component takes `labels`, a partial object that is merged over the English defaults: `Inbox`,
`ChatThread`, `TeamThread`, `ThreadPanel`, `Composer`, `MessageList`, `MessageActions`,
`Reactions`, `MarkdownBody` and `AssistantThread`. Keep the object stable (module level or
`useMemo`), as noted above for long threads.

Labels that depend on a number or a person are functions, so the translation can inflect them:
`Inbox` `labels.unread(count)`, `TeamThread` `labels.replies(count)`, `ChatThread`
`labels.repliedTo({ author, original, own, toOwn })` and `MessageActions` `labels.more({ author, own })`.
Times, dates and file sizes follow `locale`, on each list or for every component at once in
`MessagesProvider` (see [Dates and time zones](#dates-and-time-zones)).

```tsx
<ChatThread
  messages={messages}
  users={users}
  currentUserId="me"
  locale="de"
  labels={{ you: 'Du', log: 'Nachrichten', newMessages: 'Neue Nachrichten', failed: 'Nicht gesendet' }}
/>
```

The types are `InboxLabels`, `ChatThreadLabels` and so on, or `Inbox.Labels`.

## Dates and time zones

Times, "Today" and "Yesterday" dividers, inbox times and "5 minutes ago" depend on three settings:
the locale, the time zone and the current moment. `MessagesProvider` sets them for every component
below it, the way `DatesProvider` does for `@mantine/dates`:

- `locale`: `'en'` by default, for times, dates and file sizes
- `timeZone`: an IANA name such as `'America/New_York'`; it decides the time shown and where each
  day starts. Without it the runtime's zone is used
- `now`: the moment "Today", "Yesterday", weekdays and relative times count from; the current time
  by default

`ChatThread`, `TeamThread`, `ThreadPanel.Replies`, `Inbox` and `MessageList` also take `locale` and
`timeZone` props, and `Attachments` takes `locale`; a prop wins over the provider. `useMessagesContext`
returns the settings with `getLocale(prop)` and `getTimeZone(prop)` for your own rows.

```tsx
import { MessagesProvider } from 'mantine-messages';

function App({ children, user }) {
  return (
    <MessagesProvider settings={{ locale: user.locale, timeZone: user.timeZone }}>
      {children}
    </MessagesProvider>
  );
}
```

### Server rendering

A server renders in its own time zone and at its own moment, and the browser hydrates in the
reader's, so a page that shows "9:30 PM" on the server and "11:30 AM" in Tokyo, or "Today" a second
before midnight and "Yesterday" after, fails hydration. Pass the same settings to both renders:
the reader's `timeZone` (from their profile or a cookie) and the server's `now`, sent with the page.
To keep relative times moving after hydration, update `now` in state from an effect, for example
every minute with `useInterval` from `@mantine/hooks`. Keep `settings.now` the same `Date` between
renders otherwise, since memoized rows render again when it changes.

The demo below fixes `now` at 15:30 UTC and switches `timeZone`. The times move with the zone,
and so do the dividers: in Tokyo it is already past midnight, so "Morning! Any luck with that
invoice?" moves under Yesterday and only the last two messages are Today.

## Keyboard

Every action is reachable without a pointer.

- Composer and AssistantThread editor: Enter sends, Shift+Enter adds a line, and Enter during an
  IME composition does not send. Escape cancels a reply in `Composer` and an edit in
  `AssistantThread`
- Message actions: one tab stop per toolbar; the arrow keys, Home and End move between the buttons
- Thread panel: focus moves to its title when it opens from a control and goes back when it
  closes; Escape does not close it
- Shell aside: while it is collapsed and open over `Main`, Escape closes it, from the aside or from
  `MessagesShell.AsideToggle`
- Quotes, thread summaries, conversations and reactions are buttons, so Enter and Space work

`jumpTo` moves keyboard focus to the item it scrolls to, so screen readers read it and Tab
continues from there.
